## 0. 한 줄 요약

확정된 **풍부한 다색 풀로고**(`logo.png` 또는 락업)를 다크 배경에서 읽히게 만드는 다크 변형을, **이미지 생성이 아니라 결정론적 팔레트 리맵**으로 만든다 — 로고의 평면 소스색(예: 코코아·캐러멜·크림)을 브랜드 **다크 팔레트의 정확한 hex**로 영역별 치환하고, 경계는 **엣지 보간**(가장 가까운 두 소스색 사이 비율 블렌드)으로 매끄럽게 한다. 색 매칭은 **OKLab 지각 공간**에서 한다. 구조 재설계(예: 다크에선 배지 채움 제거)가 필요한 소수 로고만 **생성 폴백**. 사용처는 **큰 풀로고**(다크모드 헤더·히어로·푸터). 소유는 design-logo, 비율·균형은 에이전트 프리뷰 게이트로 검수·승인.

## 1. 동기 & 문제

- 제시용 레시피 A로 로고는 풍부한 다색이 됐다. 그런데 **풍부한 다색 풀로고는 다크 배경에서 깨진다** — 어두운 코코아 획·프레임·워드마크 글자가 다크 표면에 묻힌다(선검증에서 실증: 자체 어두운 배지가 없는 로고일수록 심함).
- **단색 레이어**(favicon·app-icon·페이지내 작은 마크)의 다크는 🅱-ii가 단색 마스터 + mask 재색으로 이미 해결. **남은 건 큰 풀로고의 다크모드.**
- 풀로고는 다색이라 단색 mask 재색이 안 통한다 → 영역별 다색 재색이 필요한데, 그게 가능한지가 미검증 가정이었다(아래 §2).

## 2. 선검증 결과 (2026-06-07, PASS)

SugarLoop 더미 브랜드로 실증(`.scratch/b2-preverify/`, gitignore — 결론만 기록):

| 검증 | 결과 |
|---|---|
| 라이트 다색 로고를 다크 배경에 그대로 | ❌ 어두운 획·워드마크 대비 소실(다크 변형 필요 확정) |
| **생성 다크 변형 — 어댑트**(`logo.png` 첨부 `--image --input-fidelity high`) | △ 같은 로고로 읽히나 **색 hex 부정확·채도 손실(크림 과다, 물빠짐)**. hue는 유지되나 명도 플립 위주 |
| 생성 다크 변형 — 별도 생성 | ❌ 정체성 드리프트(형태가 다른 로고처럼) |
| **결정론 팔레트 리맵 — 영역별 정확 hex** | ✅ **됨** — 임의 팔레트(틸/골드/블랙)로 형태 유지·정확 색 치환 실증 |
| 리맵 + 엣지 보간(2앵커 선분 블렌드) | ✅ 하드 배정의 경계 speckle 해소, 매끄러운 AA |
| 무의존 PNG 처리 | ✅ `image-gen/scripts/autocrop.mjs`의 `decodePNG`/`encodePNG` 재사용 |

**결론**: 다색 다크 변형은 **결정론 리맵**이 생성보다 우월 — 정확한 브랜드 hex, 재현성(diff 가능), 드리프트 0, API 비용 0. 단 리맵은 *색 교체*지 *구조 재설계*가 아니다.

**가정 반증 기록**: 이전 스펙(A §6 line 70, 🅱-ii §3·§4.6)은 "풍부한 다색 다크 = 재색 불가, **디자인된 다크 2장**"이라고 적었으나, 이는 *착수 전 선검증 필요*로 표시된 **미검증 가정**이었다. 본 실험이 그 선검증이며 결과는 "**영역 리맵 + 엣지 보간으로 가능**" — 가정은 반증됐다. 따라서 방향을 **결정론 리맵 기본 + 생성 폴백**으로 전환한다.

## 3. 목표 / 비목표

**목표(🅱-i)**
- 확정 라이트 풀로고에서 **다크 변형을 결정론 팔레트 리맵으로 생성**: 영역 소스색 → 브랜드 다크 팔레트 hex, **OKLab** 색 매칭, **엣지 보간**.
- **에이전트 프리뷰 게이트**: 큰 사이즈 + 다크 배경으로 렌더·http 스크린샷·자가판정·미세조정 → 사용자 평이한 승인.
- **생성 폴백**: 구조 재설계가 필요한 소수 로고는 어댑트 생성(`--image --input-fidelity high`).
- design-logo 소유, 자기 자산 파일만 생산(HTML 무편집 불변식 유지).

**비목표(→ 별도)**
- 단색 레이어 다크(🅱-ii 완료), 타입 게이트 8종(🅲).
- 라이트/다크 색 토큰 **자동 도출** — 브랜드 다크 팔레트는 사용자/토큰이 정의(자동 명도 반전 같은 건 비범위).
- 진짜 융합 baked 락업, PNG→SVG 트레이서(🅱-ii 단색 마스터 전략이 대체 — 정식 드롭).

## 4. 결정

### 4.1 소유 · 흐름
- **소유 = design-logo**(스펙 A §6 "로고 시스템 소유 유지"). 🅱-ii와 같은 집.
- design-logo 흐름 **단색 자산 단계(흐름 11) 다음에 흐름 12(다크 변형)** 추가:
  1. 라이트 풀로고 lock 후, **소스 앵커 추출**(상위 N 양자화 + 유사색 병합으로 자동 검출, 또는 지정).
  2. 각 소스 앵커 → **브랜드 다크 팔레트** 타깃 hex 매핑.
  3. **OKLab 2앵커 엣지 보간 리맵** → `candidate/logo/logo-dark-candidate.png`.
  4. **프리뷰 게이트**: 큰 사이즈 + 다크 배경(+ 라이트 원본 나란히)으로 렌더, **라이브 서버(http)** 로 `web-publisher-qa` 스크린샷 → 가독·정체성 자가판정 → 부족하면 매핑/앵커 조정·재리맵 → 사용자에게 제시(평이한 승인만).
  5. 승인 → `assets/logo/logo-dark.png` lock. 구조 재설계가 필요하다고 판단되면 **생성 폴백**으로 전환(어댑트).

### 4.2 자산 토폴로지 (`.design/assets/logo/`)
| 파일 | 내용 | 신규 |
|---|---|---|
| `logo.png` | 라이트 풀로고(기존) | — |
| `logo-dark.png` | 다크 변형(리맵 또는 생성 폴백) | **신규** |

(워드마크·락업 다크 처리는 §7 열린 질문 — 우선 풀로고 1파일로 출하.)

### 4.3 리맵 스크립트
- `skills/design-logo/scripts/remap-logo-dark.mjs` — `../../image-gen/scripts/autocrop.mjs`의 `decodePNG`/`encodePNG` 재사용(의존성 0).
- 핵심:
  - **OKLab 거리**로 각 불투명 픽셀의 1·2위 소스 앵커 판정(RGB 유클리드 대신 — 갈색계 근일직선 팔레트 안정화).
  - **2앵커 선분 보간**: 픽셀을 src_i→src_j에 투영한 t로 dst_i↔dst_j 블렌드(OKLab에서 보간 후 sRGB로). alpha 보존.
  - 색 입력 = **앵커→타깃 hex 매핑**을 인자로(스크립트는 brand-tokens.json을 모름 — 범용 변환기, design-logo가 매핑 구성).
- CLI + 라이브러리 양형(테스트 가능). PoC: `.scratch/b2-preverify/palette-remap2.mjs`(RGB·2앵커) — 프로덕션은 OKLab로 격상.

### 4.4 브랜드 다크 팔레트 입력
- 다크 타깃 색은 **사용자/brand-tokens 정의**. 표현 방식(brand-tokens.json `darkPalette` 블록 vs design-logo가 매핑을 묻기)은 §7 열린 질문. 자동 명도 반전은 안 함(룩이 브랜드마다 달라 결정 불가).

### 4.5 생성 폴백
- 리맵은 *색 교체*다. 다크모드에서 **구조 변경**(배지 채움 제거, 아웃라인 추가, 강조 요소 교체 등)이 필요한 로고는 리맵으로 안 된다 → **어댑트 생성**(`logo.png` 첨부 `--image --input-fidelity high`, "다크 배경용 재설계, 구성·정체성 유지")으로 전환. 단 색 hex는 부정확함을 감수(생성의 본질적 한계).
- 트리거: 프리뷰 게이트에서 "리맵으론 다크 룩이 안 산다"고 에이전트/사용자가 판단할 때(기준은 §7).

### 4.6 프리뷰 게이트
- **사용처 = 큰 풀로고**(다크모드 헤더·히어로·푸터)이므로, 프리뷰는 **큰 사이즈**로 다크 배경에서 본다(작은 사이즈 논리 폐기 — 거긴 🅱-ii 단색이 담당). 경계 보간 품질이 큰 사이즈에서 보이므로 보간을 기본 채택.
- mask 류와 달리 리맵 산출물은 일반 PNG라 file://도 보이지만, QA 일관성 위해 http 서빙 유지.

### 4.7 사용처 · 스왑
- 다크모드 HTML이 `prefers-color-scheme`로 `logo.png` ↔ `logo-dark.png`를 스왑한다(또는 `<picture><source media>`). brand-kit overview/제품 head·헤더 지침에 스니펫 문서화. design-logo는 파일만 생산, HTML 무편집.

## 5. 아키텍처 / 소유 · 불변식

- **다크 변형 생성**(리맵/폴백) = design-logo 소유(자기 흐름·자기 스크립트·자기 프리뷰 뷰).
- **리맵 = 결정론**: 같은 입력(라이트 로고 + 앵커→타깃 매핑) → 같은 출력. 재현·diff·정확 hex. 생성 폴백만 비결정.
- **HTML 무편집 불변식**: design-logo는 `assets/logo/logo-dark.png`만 생산. 스왑 마크업은 brand-kit/제품이 저작(consume).
- **자산 단일 소스**: 다크 변형은 라이트 `logo.png`에서 파생(라이트가 진실, 다크는 함수).

## 7. 열린 구현 질문 (플랜에서 확정)

1. **OKLab 변환 정확식**(sRGB→linear→LMS→OKLab) + 보간을 OKLab에서 할지 sRGB에서 할지.
2. **3색 교차점 처리** — 2앵커 선분 보간의 한계(3색 혼합 코너에서 틀린 중간색). 2앵커 유지 + 허용 오차로 갈지, N앵커 가중 평균으로 갈지. 선검증에선 2앵커로 충분해 보였으나 큰 사이즈 코너 재확인 필요.
3. **소스 앵커 검출** — 자동(상위 N 양자화 + OKLab 유사 병합)의 N·병합 임계 vs 지정 규약. 평면 로고 전제(레시피가 보장).
4. **브랜드 다크 팔레트 표현** — brand-tokens.json `darkPalette`/매핑 블록 vs design-logo가 게이트에서 매핑 구성. 라이트→다크 매핑을 어디에 저장(재현성).
5. **엣지 보간 alpha 임계**(`<8` 류) + 반투명 경계 처리.
6. **생성 폴백 트리거 기준** — "리맵으론 안 됨"을 게이트에서 어떻게 판정·명문화.
7. **워드마크/락업 다크** — 풀로고 1파일 외에 워드마크·락업 다크가 필요한지(우선 비범위, 필요 시 후속).

## 8. 성공 기준

확정 라이트 풀로고에서 다크 변형이 **결정론 리맵**(브랜드 다크 팔레트 정확 hex, OKLab, 엣지 보간)으로 생성돼 큰 사이즈 다크 배경에서 또렷이 읽히고 정체성을 유지한다. 에이전트가 가독·균형을 맞춰 제시하면 사용자는 평이한 승인만으로 다크 로고를 확정한다. 구조 재설계가 필요한 로고는 생성 폴백으로 처리된다. 같은 입력은 같은 다크 로고를 재현한다.
