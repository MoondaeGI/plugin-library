# Customer 페르소나 평가 도구 — 설계

- 날짜: 2026-06-09
- 상태: 설계 확정(구현 전)
- 구현 위치: `plugins/personal/`
- 선행 논의: `personal:idea` 4라운드 + `personal:discussion` 1라운드(devils-advocate)로 압박 검증됨

## 1. 목적·성격

제품 개발자가 설계·구현 단계에서, **구현을 모르는 "고객"의 눈으로** UX와 아이디어를 점검하는 도구.

- **리서치 대체가 아니다.** 발상/가설 생성기다. 정확성이 아니라 **발상 커버리지**가 목적.
- 출력은 "검증 데이터"가 아니라 **"이런 관점도 있다"는 자극**.
- 모든 출력에 *"실제 고객 아님 · 가설용"* 라벨을 강제한다(검증 데이터 오인 방지).

## 2. 구성요소

```
.personal/customer/personas.md      페르소나 데이터 (도구 중립, 단일 원천)
customer 서브에이전트 (1개·재사용)    clean-context 배우. 인간 채널 Playwright만 쥠
references/customer-core.md          공유 코어 — 아래 모든 규칙의 소유자
create-customer (스킬)               페르소나 저작/수정 진입점
check-customer-ux (스킬)             UX 비평 무대감독
check-customer-idea (스킬)           아이디어 탐색 무대감독
```

각 단위의 책임:

| 단위 | 무엇을 하나 | 어떻게 쓰나 | 무엇에 의존하나 |
|---|---|---|---|
| `personas.md` | 페르소나 데이터 보관 | 스킬이 읽고/쓴다 | 없음(데이터) |
| `customer` 서브에이전트 | 격리된 배우로 반응 생성 | 무대감독이 디스패치 | 디스패치 페이로드 + 인간 채널 Playwright |
| `customer-core.md` | 창작 절차·표면 조립 규칙·툴 화이트리스트·출력 규칙·가드 소유 | 모든 스킬이 읽음 | 없음(레퍼런스) |
| `create-customer` | 페르소나 작정 저작·수정·리스트 | 사용자가 단독 호출 | core, personas.md |
| `check-customer-ux` | UX 비평 무대 | 사용자가 영역 지정 호출 | core, personas.md, customer 서브에이전트, (옵션)Playwright MCP |
| `check-customer-idea` | 아이디어 탐색 무대 | 사용자가 컨셉 지정 호출 | core, personas.md, customer 서브에이전트 |

## 3. 역할 분리 (이 설계의 심장)

격리 자체가 가치가 아니라 **표면 조립 규칙이 충분조건**이다. 격리는 필요조건.

- **무대감독 스킬(메인 컨텍스트)** — 구현을 알지만, customer에게 넘길 "표면"을 조립할 때 **타입 A는 빼고 타입 B는 넣는다.** 이후 customer 서브에이전트를 디스패치.
- **customer 서브에이전트(격리)** — 페르소나 + 보여준 표면 + 인간 채널 도구만 안다. 구현 토큰이 컨텍스트에 물리적으로 없음.

### 표면 조립 규칙 (customer-core.md 소유)

| 타입 A — **빼기** (구현 지식) | 타입 B — **넣기** (도메인 멘탈모델) |
|---|---|
| 코드·아키텍처·내부 함수 호출·성능 근거·DOM·HTML·네트워크 | "이건 X류 앱이다", 그 부류 고객이 *당연히 갖는 기대* |
| 예: "DB 인덱스가 있어 빠를 것", "saveNote() 호출" | 예: "노트앱이면 검색되겠지", "저장 누르면 안전 보관되겠지" |

핵심 한 줄: **"어떻게 만들었나(A)는 빼고, 무슨 부류 제품이라 뭘 기대하는가(B)는 넣는다."**
- A가 새면 → 고객이 개발자가 됨(오염).
- B가 빠지면 → 고객이 "픽셀에만 반응하는 백지"가 되어 실제 고객보다 *덜* 현실적이 됨.

## 4. Playwright — "인간 채널"만

UX는 멈춘 프레임이 아니라 **흐름·전환·조작 중 마찰**에서 드러난다. 따라서 customer가 **직접 조작하며 탐색**한다(정적 스크린샷 전달보다 우월). 단, 실제 고객은 눈과 손으로만 제품을 쓰므로 도구를 인간 채널로 제한한다.

| 허용 (눈·손) | 금지 (구현 X-ray = 타입 A) |
|---|---|
| 스크린샷, 클릭, 스크롤, 타이핑, 네비게이트 | DOM 덤프, raw HTML, `evaluate`, 네트워크, 콘솔, 셀렉터 분석 |

- 이 화이트리스트를 `customer-core.md`에 못박는다 → 타입 A 차단이 **텍스트 큐레이션이 아니라 툴 권한 레벨에서 구조적으로** 강제된다.
- customer가 자기 페르소나의 호기심대로 돌아다니므로 **천장 효과(사용자 질문 범위에 갇힘)도 완화**된다.

### ⚠️ 구현 단계 검증 포인트 (writing-plans에서 확정)

Playwright MCP는 보통 a11y 스냅샷의 ref로 요소를 클릭한다. 순수 스크린샷+좌표 클릭이 가능한지 확인 필요. 불가하면 **a11y 트리를 "스크린리더 사용자가 듣는 것(=인간 지각)"으로 간주해 제한 허용**할지 결정. (DOM/네트워크/console/evaluate는 어떤 경우에도 금지.)

## 5. 데이터 흐름

### check-customer-ux
1. 페르소나 로드 — 없으면 core "빠른 모드"로 생성·주입·저장.
2. 입력 받기:
   - URL 있음 + Playwright MCP 등록됨 → **실사용 탐색**(최선)
   - 없음 → **스크린샷 첨부**로 폴백
   - 둘 다 없음 → **"시각 디테일은 추정"** 경고하고 진행
3. 표면 조립(A 빼고 B 넣고) + **영역 지정**(사용자는 "결제 플로우" 같은 *영역*만 준다 — 유도 질문 금지).
4. customer 디스패치 → 인간 채널 Playwright로 직접 조작·탐색.
5. 결과 전달: **불편 지점 + 안 물어본 인접 각도 역제기**.

### check-customer-idea
1~2. 페르소나 로드 / 컨셉·가용 데이터 받기 (Playwright 불필요).
3. 표면 조립 → 디스패치 → "이 고객이 원할 것" 발산 + 역제기.

### create-customer
core "꼼꼼 모드"로 인터뷰식 저작 — 타입 B 도메인 기대, 진짜 걱정거리, 맥락, 회의 지점까지 캐서 `personas.md`에 저장. 기존 페르소나 **수정·리스트**도 겸한다.

> 페르소나 소스 정책: 저장된 것 있으면 사용, 없으면 하나 만들어 주입·저장 후 시작. 창작 로직은 core에 **한 번만**, 진입점만 둘(단독 꼼꼼 / 인라인 빠름).

## 6. 출력 구조 (양 체크 공통, core 소유)

```
[답변] → [안 물어본 각도 역제기 1~2개] → [가설용 · 실고객 아님 라벨]
```
+ 안티-sycophancy("사용자 결론에 동조 금지")를 디스패치 페이로드에 주입.

## 7. 저장·gitignore 정책

- 위치: `.personal/customer/personas.md` (프로젝트 루트의 `.personal/` 하위, 도구 중립 단일 원천).
- `.personal/` = 이 personal 플러그인 전체의 데이터 네임스페이스. 통째로 gitignore 대상(개인 작업 공간).
- **gitignore 처리**: 스킬이 `.personal/`을 **처음 생성하는 순간 1회만** prompt — "`.personal/`을 `.gitignore`에 추가할까요? (y/N)". 답대로 따르고 **재nag 없음**.

## 8. 셋업 전제 (옵셔널 의존성)

- Playwright MCP는 **하드 의존이 아니다** — 없으면 스크린샷 폴백 → 추정 경고로 degrade(§5).
- 실사용 탐색 모드를 쓰려면:
  1. `.claude.json`의 `mcpServers`에 Playwright MCP 등록(머신당 1회).
  2. mcpServer 변경 후 **반드시 `sync-mcp` 스킬** 실행(`mcp-config.json` 동기화) — 사용자 규칙.
  3. 정확한 등록 CLI(`claude mcp add ...`)는 context7로 공식문서 확인 후 안내.

## 9. 설계 노트 (정직한 단서)

- **격리의 가치 = 오염 "제거"가 아니라 "표면 조립이라는 감사 가능한 한 경계로 국소화".** 단 Playwright 툴 화이트리스트(§4)는 그중 타입 A를 *구조적으로* 막는다.
- **지식은 구조로, 행동은 프롬프트로** — 구현 누설(지식)은 격리/툴제한으로, 시코펀시·역제기(행동)는 프롬프트로. 메커니즘에 맞춘 의도적 선택이지 일관성 결여가 아니다.
- **fresh-context는 종단 일관성이 없다**(회귀 탐지 불가 — "전보다 불편해졌다"를 못 느낌). v1 YAGNI. 후속에 "직전 반응 요약 옵트인 주입"(앵커링 비용 감수)으로 보강 가능.
- **되돌릴 수 있다** — 격리 왕복 오버헤드가 발상 커버리지를 해치면 인라인 롤플레이로 후퇴. "격리가 롤플레이를 이긴다"는 아직 가설이며, 발상 다양성/커버리지로 최소 1회 대조해 정당화할 것.
- **모달리티 비대칭** — UX(스크린샷=고객이 실제 보는 것)와 idea(텍스트 컨셉=고객이 마주하는 형태 아님)의 현실감이 다르다. 인지하고 진행.

## 10. 범위 (YAGNI)

v1 = `create-customer` + `check-customer-ux` + `check-customer-idea` + `customer` 서브에이전트 + `customer-core.md` + `personas.md`.
`check-customer-pricing` 류는 나중에 같은 코어 위에 얹는다. 처음부터 많이 만들지 않는다.

## 미해결 / 구현 단계로 넘기는 것

- Playwright MCP 클릭 메커니즘(ref vs 좌표) 실제 확인 → 인간 채널 화이트리스트 최종 확정(§4).
- `customer-core.md`의 페르소나 스키마 구체 필드.
- 스킬 frontmatter `description`(트리거 문구) 문안 — discussion/idea 컨벤션 따름.
- customer 서브에이전트 정의 파일 위치/포맷(`.claude/agents/` 표준) 및 페르소나·표면 주입 방식.
