# design-html-prototype 완전성 체크리스트 설계

날짜: 2026-06-08
대상: `design-html-prototype` (체크리스트 생성 단계 추가) + `web-publisher` (빌드 후 완전성 자가 대조 단계 추가)
관련: [html-prototype-asset-gap-design](../2026-06-07/html-prototype-asset-gap-design.md) (빌드 *전* 자산 갭 패스 — 이 설계는 빌드 *후* 구현 누락을 다룬다)

## 문제

`design-html-prototype`은 풀페이지 HTML 프로토타입의 스펙(출력 경로·섹션 구조)을 정하고 실제 저작을 `web-publisher`에 위임한다. web-publisher는 빌드 후 `web-publisher-qa`로 자가 검사하지만, 그 QA는 **"보이는 레이아웃 깨짐"(overflow·정렬·grid·깨진 이미지·겹침)만** 본다 — 충실도·완전성 판정은 명시적으로 범위 밖이다(`web-publisher-qa` SKILL.md L29·L67, `web-publisher.md` L24).

실사용 테스트에서 web-publisher가 **DESIGN.md에 정의된 섹션·요소를 통째로 빠뜨리는 *구현 누락*** 이 여러 곳 관측됐다. 산문 스펙은 부분 구현하고 "다 했다"고 착각하기 쉽다(빌더의 확증 편향). 현재 이 누락을 잡는 자동 게이트가 없어, 사람이 매번 수동으로 발견해 재수정을 요청해야 한다.

## 핵심 원칙

1. **권위는 DESIGN.md다. comp 이미지가 아니다.** 체크리스트의 앵커는 DESIGN.md의 실제 카피·섹션 정의에서만 뽑는다. comp(gpt-image 산출물 = 불완전한 한 해석)는 앵커 출처로 쓰지 않는다 — 그래야 "정확히 fetch한 자산을 comp의 틀린 자산에 맞춰 되돌리는" 함정(2026-06-07 spec L74 결함(1))을 피한다.
2. **검사는 결정적(deterministic)이다. 비전이 아니다.** "섹션·요소가 통째로 빠짐"은 곧 `index.html`에 그 마크업·헤딩·핵심 문구가 **없다**는 뜻이고, Read/Grep으로 100% 신뢰도로 잡힌다. 스크린샷 비전(fold·렌더타이밍·플레이스홀더 노이즈에 흔들림)보다 더 신뢰성 높고 싸다.
3. **자동 탐지 + 자동 수정을 web-publisher *자기 맥락 안에서* 한다.** 미충족 항목은 web-publisher가 스스로 구현 추가 → 재대조하는 내부 루프로 닫는다. 메인이 리뷰어↔빌더를 왕복 재디스패치하는 핸드오프 루프가 아니다(2026-06-07 spec L75가 그 핸드오프를 불필요하다고 폐기).
4. **기준의 권위와 빌드를 분리한다.** "무엇이 있어야 하나"(체크리스트)는 `design-html-prototype`이 만들고, "빌드"는 web-publisher가 한다. web-publisher는 외부에서 받은 체크리스트를 기계적으로 대조할 뿐이라, 신규 독립 리뷰어 에이전트 없이도 *기준 ≠ 빌더* 라는 독립성이 지켜진다.

## 흐름

```
design-html-prototype
  1. 스펙 확정 (기존: 출력 경로·섹션 구조)
  2. 자산 갭 패스 (기존: 2026-06-07 — 빌드 전 자산 조달·매니페스트)
  3. ★완전성 체크리스트 생성 (신규, 빌드 전):
       DESIGN.md → 필수 섹션 + 섹션별 핵심 헤딩·문구 앵커 + 핵심 요소
       → 빌드 스펙에 인라인으로 실어 web-publisher에 전달 (권위 = DESIGN.md만)
  4. web-publisher 위임: 섹션 구조 + 매니페스트 + ★완전성 체크리스트
  5. web-publisher: 구현 → layout-QA(web-publisher-qa) → ★완전성 자가 대조 → 미충족 시 내부 수정 루프
  6. 사람이 브라우저로 최종 확인 (기존 게이트) — 열거 불가 잔여만
```

## 완전성 체크리스트 (design-html-prototype 산출)

`design-html-prototype`이 DESIGN.md를 읽어 섹션 구조를 정할 때(SKILL.md §섹션 구조), 함께 만든다. 항목 종류:

- **필수 섹션** — DESIGN.md가 기술한 화면의 섹션 목록(예: `hero`·`problem`·`mechanism`·`features`·`dashboard-preview`·`cta`·`footer`). 랜딩이 아니면 화면 유형에 맞게 조정.
- **핵심 헤딩·문구 앵커** — 섹션별로, DESIGN.md의 *실제 카피*에서 뽑은 distinctive 문자열(섹션 제목·핵심 CTA 문구 등). DESIGN.md가 권위이므로 web-publisher는 이 카피를 그대로 써야 하고, 따라서 verbatim 대조가 공정하다.
- **핵심 요소** — 그 화면에 반드시 있어야 하는 인터랙티브·구조 요소(예: CTA 버튼, 내비 링크, 플랜 카드 N개, 폼 필드 등).

형식: **v1은 별도 파일 없이 빌드 스펙에 인라인**으로 전달한다(아티팩트를 늘리지 않음). 섹션 present-but-empty는 헤딩·문구 앵커가 안 잡혀 미충족으로 드러나므로, 섹션 class만이 아니라 *앵커*를 함께 넣는 게 중요하다.

> 향후 체크리스트가 커지거나 사람이 "요구 vs 충족"을 보고 싶어지면 파일로 승격할 수 있으나 v1 범위 밖.

## web-publisher 완전성 자가 대조 (web-publisher 산출)

기존 흐름(구현 → layout-QA → 수정 반복 → 완료)에 **완전성 차원**을 한 단계 추가한다.

1. layout-QA(web-publisher-qa) 통과 후, 빌드된 `index.html`을 **Read/Grep으로** 각 체크리스트 항목 존재를 대조한다.
2. 미충족 항목이 있으면 **자기 맥락에서** 구현을 추가하고(외과적), layout-QA + 완전성 대조를 다시 돈다.
3. 모든 항목 충족 시 완료. 최종 메시지에 **충족/미충족 표**를 보고한다.
4. **만들 수 없는 항목**(필요 자산 부족 등)은 손으로 지어내지 말고 기존 "매니페스트 밖 갭은 멈춰 보고" 규칙으로 에스컬레이션한다 → 상위 스킬의 자산 갭 패스로 되돌린다.

**경계 일관성**: 존재 대조(presence)는 *미적·충실도 판정이 아니므로* web-publisher의 "보기 좋은가는 판정 안 함"(web-publisher.md L53) 경계와 충돌하지 않는다. "있어야 할 게 있나"는 객관·기계적 판정이고, "예쁜가/충실한가"는 여전히 designer·사람 몫이다.

## 바뀌는 파일

- **수정** `skills/design-html-prototype/SKILL.md` — "흐름(리뷰 게이트)" 절에 완전성 체크리스트 생성 단계 추가 + "HTML 산출 위임" 절에 "체크리스트를 빌드 스펙에 함께 넘긴다" 명시 + 인트로에 한 줄 반영.
- **수정** `agents/web-publisher.md` — "흐름"에 완전성 자가 대조 단계(layout-QA 다음) 추가 + 입력 목록에 "완전성 체크리스트(상위 스킬이 스펙으로 전달)" 추가. frontmatter(model·tools)는 무변경.
- **무변경** `web-publisher-qa`(레이아웃 전용 유지), **신규 에이전트 없음**.
- `web-publisher.md` *본문*이 바뀌므로 `npm run sync`로 `codex-agents/web-publisher.toml`(본문을 미러링)을 재생성해야 한다(frontmatter `model`·`tools`는 무변경이라 TOML에 영향 없음). 갱신은 Claude `/reload-plugins`, Codex `npm run codex:reinstall`.

## 2026-06-07 spec과의 관계 (왜 어제 버린 것과 다른가)

2026-06-07 `html-prototype-asset-gap-design`의 "버린 대안" 절은 두 가지를 폐기했다:

1. ❌ **빌드 후 "렌더 ↔ comp" vision-diff 게이트** — 결함(1) comp는 정답 아님, 결함(2) 비전 신뢰도 낮음.
2. ❌ **fidelity-verify 신규 스킬 / 라운드 루프** — "빌드 후 갭은 비율 문제뿐(=layout-QA 영역)"이라는 전제 하에 post-hoc 루프·재전달 핸드오프 불필요.

이 설계는 둘 다 *되살리지 않는다*:

- **결함(1) 회피** — 권위가 comp가 아니라 **DESIGN.md**다(원칙 1). comp는 앵커 출처로 안 쓴다.
- **결함(2) 회피** — **비전이 아니라 결정적 Read/Grep**이다(원칙 2). 비전 신뢰도 문제 자체가 없다.
- **핸드오프 불필요 회피** — 수정 루프가 **web-publisher 자기 맥락 내부**다(원칙 3). 메인↔리뷰어 재디스패치 핸드오프가 없다.
- **전제 보완** — 2026-06-07은 "web-publisher가 스펙을 충실히 구현한다 → 빌드 후 갭은 비율뿐"을 전제했으나, 실사용 테스트가 *구현 누락(통째 빠짐)* 으로 그 전제를 깼다. 이 설계는 그 빈틈만 결정적으로 메운다.

## 버린 대안 (이번 논의)

`devils-advocate` 압박 검증 후 폐기:

- ❌ **신규 vision 리뷰어 서브에이전트 + 메인 주도 자동수정 루프 + comp 버킷 분류.** (a) "comp엔 있고 DESIGN.md와 모순 없음 → 자동 수정" 버킷이 comp를 수정 근거로 끌어들여 결함(1)을 부활시킨다. (b) 재사용하려던 `screenshot.mjs`는 `--window-size=w,1100` + `--screenshot`이라 viewport(상단 1100px)만 캡처해 fold 아래 섹션을 못 보므로 "렌더에 없음"과 "스크린샷에 안 담김"을 구분 못 한다. (c) 통째 누락은 비전보다 Read/Grep이 더 신뢰성 높고 싸다 — 비전 리뷰어가 ①에 과잉, ②에 위험. (d) web-publisher는 서브에이전트 디스패치 도구가 없어(web-publisher.md L4) 매 라운드 빌드 맥락 없는 새 인스턴스로 재디스패치되는 핸드오프 비용.
- ❌ **A + report-only 독립 리뷰어(자동수정 없이 사람에게 의심 목록만).** 열거 불가 케이스(내용 오류·미열거 누락·CSS로 가려 안 보임)를 사람에게 미리 정리해 주는 가치는 있으나, viewport 스크린샷·비전 신뢰도 한계가 그대로 남고, 관측된 문제(열거 가능한 통째 누락)는 A가 이미 자동으로 닫는다. "써보고 부족하면 나중에 추가"로 보류.

## 범위 밖

- **섹션은 있는데 내용이 미묘하게 틀린 경우 / 체크리스트에 안 적은 누락 / CSS로 가려 안 보이는 경우** — 어떤 자동화도 신뢰성 있게 못 잡는 잔여. 기존 사람 브라우저 확인 게이트가 담당한다.
- **미적·디자인 충실도 판정** — designer·사람 몫(불변).
- **web-publisher-qa(layout-QA) 변경** — 그대로 둔다.
- **체크리스트 파일 영속화·"요구 vs 충족" 리포트 UI** — v1 인라인으로 충분. 필요해지면 후속.
