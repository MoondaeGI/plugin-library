# idea 스킬 설계

**상태:** 설계 확정 (구현 전)
**날짜:** 2026-06-08

## 목적

날 것의 아이디어를 `brainstorming`(본격 설계)으로 넘기기 전에, `devils-advocate`
서브에이전트로 라운드를 돌며 단점을 압박 검증하고 사용자와 합의에 도달하는
**수렴 루프 오케스트레이터**.

기존 `discussion` 스킬과의 차이:

- `discussion` = *이미 굳히려는 결정·설계*를 압박 검증 (의견 → 딴지 → 응답).
- `idea` = *아직 설계 이전인 날 것의 아이디어*를 brainstorming 넘기기 전에 검증.

둘은 같은 `personal:devils-advocate` 에이전트를 **조합**하지만 쓰는 *순간*이
다르다. 비판 로직은 에이전트에 있으므로 두 스킬 간 코드 중복은 없다.

## 흐름

```
진입: 사용자가 아이디어 제시
[루프]
 1. 이해   — 딴지가 물어뜯을 거리가 생길 만큼만 가벼운 질문(한 번에 하나).
            직전 라운드의 합의/수정을 반영해 아이디어를 정련.
            ※ 풀 요구사항 elicitation 금지 — 그건 brainstorming 몫.
 2. 딴지   — devils-advocate 라운드 (응답 전문 그대로 전달)
            · 첫 라운드: Agent 도구로 personal:devils-advocate 새 디스패치,
              검증 대상 = 정련된 아이디어(+필요 시 사용자 프레이밍), 에이전트 ID 기억
            · 이어지는 라운드: 같은 에이전트에 SendMessage (해소된 반론 재탕 방지)
            · 주제가 크게 바뀌면 새 디스패치
 3. 합의   — 기본: 중립 진행자 ("이 반론들 어떻게 보세요?")
            반응형: 사용자가 질문/의견을 내면 Claude도 본인 의견 제시 or 반론으로 밀어붙임
            합의가 더 필요하면 → 1로 (다음 라운드)
[종료 — 합의 단계에서 사용자 선언 감지]
 · "포기/그만" 류  → 세션 종료 (산출물 수정 없음)
 · "구현/가자" 류  → brainstorming 핸드오프 (아래 참고)
```

## 각 단계 상세

### 1. 이해

- 한 번에 질문 하나. 딴지가 구체적으로 공격할 수 있을 만큼의 최소 이해만 확보한다.
- 풀 요구사항·설계 질문은 하지 않는다 (brainstorming과 역할 분담 — 중복 방지).
- 2라운드 이후엔 직전 합의/수정 사항을 반영해 아이디어를 다시 한 문장으로 정련한다.

### 2. 딴지 (devils-advocate)

- 비판을 Claude가 직접 쓰지 않는다 — **반드시** `personal:devils-advocate` 디스패치
  (`discussion`과 동일 원칙). 자가 비판은 독립성을 깨므로 금지.
- 라운드 처리는 `discussion`의 "라운드 처리"를 차용:
  - 첫 라운드 / 새 주제 → `Agent` 새 디스패치, ID 기억.
  - 같은 주제의 다음 라운드 → `SendMessage`로 이어 호출 (백지 재디스패치 시
    이미 해소한 반론이 되돌아오는 문제 방지).
- 에이전트 응답은 **전문 그대로** 출력한다(steelman / 심각도순 반론 / 인정하는
  부분 / 가장 위험한 단일 허점 / 종합 판정). 요약·발췌·심각도 희석 금지.

### 3. 합의

- **기본 자세 = 중립 진행자.** Claude는 자발적으로 평가·판정을 내리지 않고
  "이 반론들 어떻게 보세요?"로 사용자의 판단을 끌어낸다. 평가는 사용자 몫.
- **반응형.** 단, 사용자가 합의 과정에서 질문하거나 의견을 내면 Claude는 수동
  릴레이로 멈추지 않고 실질적으로 응답한다 — 본인 의견을 제시하거나 반론으로
  밀어붙인다.
- 합의 단계에서 산출물(코드·파일)을 직접 수정하지 않는다. brainstorming 전까지
  구현 행위 없음.

### 종료 분기

매 라운드 합의 단계에서 사용자의 종료 선언을 감지한다.

- **포기** ("그만", "접자", "포기" 류) → 스킬 종료. 산출물 수정 없음.
- **구현** ("가자", "구현하자", "설계로 넘어가자" 류) → brainstorming 핸드오프.

## brainstorming 핸드오프 (graceful 조건부 의존)

`superpowers`에 하드 의존하지 않는다. `idea`의 핵심 가치(이해 → 딴지 수렴 루프)는
superpowers와 무관하게 자체 완결이며, brainstorming은 마지막 출구 램프일 뿐이다.

- 사용 가능한 스킬 목록에 `superpowers:brainstorming`이 **있으면** → 그것으로
  핸드오프하며, 누적된 이해 + 합의점 + 살아남은 우려(미해소 🔴/🟡)를 컨텍스트로
  넘겨 brainstorming이 기초를 다시 묻지 않게 한다.
- **없으면** → "이제 설계 단계입니다. 설계/brainstorming 워크플로로 진행하세요"
  라는 일반 핸드오프로 폴백한다.

이는 마크다운 지시문이고 모델이 런타임에 사용 가능 스킬 목록을 보므로,
"있으면 A, 없으면 B" 조건부 지시로 표현된다.

## 의존성

- **`personal:devils-advocate` (필수)** — 이 repo 내부 에이전트. 비판 핵심.
- **`superpowers:brainstorming` (선택, 있으면 향상)** — 구현 핸드오프를
  매끄럽게 한다. 없어도 검증 루프는 그대로 동작.

## 산출물 / 작업

- `skills/idea/SKILL.md` 신규 (공통 프론트매터 `name`, `description`).
- README(또는 해당 문서)에 의존성 한 줄: superpowers는 선택 — 있으면 핸드오프
  향상, devils-advocate는 동일 repo라 별도 설치 불요.
- `npm run sync`로 Codex 번들(`plugins/personal/`) 재생성. 커밋은 소스(`skills/`)만
  (번들은 gitignore된 로컬 생성물).

## 비목표 (YAGNI)

- `idea`가 풀 요구사항 elicitation을 하지 않는다 (brainstorming 영역).
- `idea`가 코드·파일을 직접 수정하지 않는다.
- `discussion`을 변경하지 않는다 (정체성 분리 유지).
- 자동 트리거 보장은 목표가 아니다 — 명시적 호출 전제 (description 문구로 발견성만 개선).
