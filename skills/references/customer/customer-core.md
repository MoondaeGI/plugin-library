# customer-core

customer 페르소나 평가 도구의 **공유 코어**. 세 스킬(`create-customer`, `check-customer-ux`, `check-customer-idea`)이 `../references/customer/customer-core.md`로 참조한다. 세 스킬은 **메인 컨텍스트의 "무대감독"** — 구현을 알지만, 격리된 `customer` 서브에이전트(배우)에게 넘길 "경험 표면"을 조립할 때 규칙을 지킨다. 이 문서는 **무대감독 측 규칙만** 소유한다. 배우 측 규칙(캐릭터 유지, 구현 추론 금지, 출력 강제)은 `agents/customer.md`가 소유하므로 여기 쓰지 않는다.

## 이 도구의 성격 (먼저 못박는다)

- **리서치 대체가 아니다. 발상/가설 생성기다.** 목적은 정확성이 아니라 **발상 커버리지**.
- 출력은 "검증 데이터"가 아니라 **"이런 관점도 있다"는 자극**이다.
- 모든 최종 출력에 *가설용 · 실고객 아님* 라벨을 강제한다(아래 §7). 검증 데이터로 오인되면 이 도구는 해롭다.

## 설계 한 줄 원칙

> **지식은 구조로, 행동은 프롬프트로.**
> 구현 누설(지식)은 격리·툴 제한으로 막고, 시코펀시·역제기(행동)는 프롬프트로 지시한다.

## 1. 페르소나 스키마

한 페르소나는 다음 필드로 구성된다.

| 필드 | 내용 |
|---|---|
| `slug` | 짧은 식별자(소문자·하이픈). 예: `busy-clinic-nurse`. personas.md 헤더와 디스패치에서 키로 쓴다. |
| 한 줄 정체성 | 나이·역할·조직 유형을 한 줄로. 예: "38세, 중소 병원 외래 간호사". |
| 가장 큰 걱정 1~2 | 이 사람이 일·삶에서 진짜로 신경 쓰는 것. 제품 기능이 아니라 **사람의 걱정**. 예: "교대 중 환자 누락", "퇴근 못 함". |
| 맥락 | 어떤 상황에서 이 제품을 접했나. 누가 권했나·왜 깔았나·언제 켜나. |
| 타입 B 도메인 기대 | **이 부류 제품이라면 당연히 갖춰져 있겠지** 하는 기대(아래 §3 타입 B). 예: "노트앱이면 검색되겠지", "저장 누르면 안전 보관되겠지". 화면을 보기 전부터 머릿속에 있다. |
| 회의 지점 | 뭘 의심하며 보나. 어디서 "이거 사기 아냐?"를 느끼나. 예: "무료라는데 광고로 도배됐겠지". |

**저장 형식 (personas.md):** 페르소나 하나당 한 블록.

```markdown
## <slug> — <한 줄 정체성>

- 가장 큰 걱정: ...
- 맥락: ...
- 타입 B 도메인 기대: ...
- 회의 지점: ...
```

여러 페르소나는 같은 파일에 `##` 헤더로 이어 쌓는다. 무대감독은 `## <slug> —` 헤더로 페르소나를 찾는다.

## 2. 페르소나 소스 정책

**저장된 것 있으면 사용, 없으면 생성.** 무대감독은 시작 시 `.personal/customer/personas.md`를 읽어 요청에 맞는 페르소나가 있는지 본다. 없으면 아래 두 모드 중 호출자에 맞는 쪽으로 만든다.

### 꼼꼼 모드 (create-customer가 호출)

- 인터뷰식으로 스키마 **전 필드를** 한 번에 **하나씩** 캐묻는다.
- **추측 금지.** 사용자가 안 준 필드를 무대감독이 지어내지 않는다 — 물어본다.
- 다 채우면 §6에 따라 personas.md에 저장한다. 기존 페르소나 **수정·리스트**도 이 모드의 일부다.

### 빠른 모드 (check-* 인라인)

- 진행에 필요한 **최소 필드만** 1~2 질문으로 확보한다: 정체성 · 핵심 걱정 · 타입 B 도메인 기대.
- 나머지 필드는 비워둔 채 진행한다(완결성보다 진행 우선).
- 점검이 끝난 뒤 "이 페르소나를 personas.md에 저장할까요?"를 **한 번** 제안한다(강요 없음).

## 3. 표면 조립 규칙 (A/B) — 이 도구의 심장

디스패치 전, 무대감독은 customer에게 줄 **"경험 표면"**을 만든다. 무대감독은 구현을 알지만, 표면에는 **타입 A는 빼고 타입 B는 넣는다.**

| 타입 A — **빼기** (구현 지식) | 타입 B — **넣기** (도메인 멘탈모델) |
|---|---|
| 코드·아키텍처·내부 함수 호출·성능 근거·DOM·HTML·네트워크·셀렉터 | "이건 X류 앱이다" + 그 부류 고객이 *당연히 갖는 기대* |
| 예: "DB 인덱스가 있어 빠를 것", "`saveNote()`를 호출", "이 div가 lazy-load됨" | 예: "노트앱이면 검색되겠지", "저장 누르면 안전 보관되겠지" |
| → 실제 고객은 **모른다.** 새면 고객이 개발자가 됨(오염). | → 실제 고객은 **반드시 갖고** 화면을 본다. 빠지면 고객이 "픽셀에만 반응하는 백지"가 됨. |

**한 줄 원칙:** **"어떻게 만들었나(A)는 빼고, 무슨 부류라 뭘 기대하나(B)는 넣는다."**

표면을 조립할 때 페르소나의 **타입 B 도메인 기대 필드도 표면에 명시**한다 — 그래야 배우가 "이 부류라면 당연히 ~겠지"라는 기대를 갖고 화면을 마주한다.

## 4. Playwright 가용성·폴백 + 인간 채널 화이트리스트

(check-customer-ux용. idea 점검에는 Playwright가 필요 없다.)

### 모드 결정

| 조건 | 모드 |
|---|---|
| URL 있음 + Playwright MCP 등록됨 | **실사용 탐색** — customer가 직접 조작하며 돌아다닌다(최선). |
| 스크린샷 첨부됨 | 그 스크린샷을 표면으로 사용한다. |
| 둘 다 없음 | **"시각 디테일은 추정"** 경고를 사용자에게 먼저 띄우고 진행한다. |

Playwright MCP는 **하드 의존이 아니다.** 미등록이어도 스킬은 폴백으로 정상 동작한다.

### 인간 채널 화이트리스트 (타입 A를 툴 권한으로 차단)

customer 디스패치 시 **아래 인간 채널 툴만 허용**한다. 실제 고객은 눈과 손으로만 제품을 쓰므로 도구도 거기에 맞춘다. 이로써 타입 A 차단이 텍스트 큐레이션이 아니라 **툴 권한 레벨에서 구조적으로** 강제된다.

**허용 (눈·손):**
`browser_navigate`, `browser_navigate_back`, `browser_take_screenshot`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_press_key`, `browser_hover`, `browser_select_option`, `browser_wait_for`, `browser_resize`, `browser_tabs`, `browser_handle_dialog`, `browser_file_upload`, `browser_drag`, `browser_drop`, `browser_fill_form`

**금지 (구현 X-ray = 타입 A):**
`browser_evaluate`, `browser_run_code_unsafe`, `browser_console_messages`, `browser_network_request`, `browser_network_requests`

메모:
- MCP 등록 시 실제 툴 이름은 `mcp__<등록명>__browser_*` 형태다(예: 등록명 `playwright` → `mcp__playwright__browser_click`).
- a11y 스냅샷(`browser_snapshot`)은 **허용**한다 — 역할·이름·라벨은 스크린리더 사용자가 지각하는 의미층이지 구현 내부가 아니다. 또한 기본 모드에서 `browser_click`이 스냅샷의 ref를 요구하므로 신뢰성·설정 단순성을 위해 둔다.
- 더 엄격한 대안(`--caps=vision`: 스냅샷 제외 + 좌표 클릭)은 후속 옵션으로만 메모해 둔다.

## 5. 디스패치 페이로드 구성

무대감독이 `customer` 서브에이전트(subagent_type는 추후 `customer`)에 넘기는 것:

1. **[페르소나]** — §1 스키마대로 채워진 페르소나(슬러그 + 필드들).
2. **[조립된 표면]** — §3대로 **타입 A 제외 / 타입 B 포함**. URL·스크린샷·"이건 X류 앱"·도메인 기대.
3. **[task]** — UX 점검이면 **"영역"**("결제 플로우" 같은), idea 점검이면 **"컨셉 + 가용 데이터"**.
4. **[출력 계약 상기]** — §7 형식을 따르라는 짧은 환기.

규칙:

- **사용자의 유도 질문을 그대로 넘기지 마라.** 점검할 **영역/주제만** 넘긴다. ("이거 너무 헷갈리지 않아?" 같은 프레이밍을 넘기면 배우가 거기에 동조하게 됨 — 천장 효과·시코펀시 유발.)
- **Agent 도구 결과는 옮겨야만 사용자에게 보인다.** customer의 응답은 **전문 그대로 전달**한다. 요약·발췌·부드럽게 다시 쓰기 금지.

## 6. 저장·gitignore

- 경로: **`.personal/customer/personas.md`** (소비 프로젝트 루트의 `.personal/` 하위 — 도구 중립 단일 원천).
- `.personal/`이 **없어서 새로 만들 때만** 1회 prompt:

  > `.personal/`을 `.gitignore`에 추가할까요? (y/N)

  - 먼저 `.gitignore`에 `.personal/` 라인이 있는지 **grep으로 확인**한다. 이미 있으면 묻지 않는다.
  - 사용자가 답한 대로 따른다(y면 라인 추가, N이면 그대로 둠).
  - **재nag 없음.** 한 번 물었으면 같은 세션·이후 호출에서 다시 묻지 않는다.
- `.personal/`이 이미 존재하면 prompt 없이 그 안에 저장한다.

## 7. 출력 계약

최종 사용자 출력 형식(무대감독이 customer 응답을 전달할 때의 형태):

```
[답변/반응]
→ [안 물어본 인접 각도 역제기 1~2개]
※ 실제 고객 아님 · 페르소나 시뮬레이션 · 가설용
```

- **[답변/반응]** — 페르소나의 반응(불편 지점, 기대 충족/배신, 원하는 것).
- **[역제기]** — 사용자가 묻지 않았지만 인접한 각도 1~2개를 먼저 꺼낸다. 천장 효과(질문 범위에 갇힘)를 깨기 위함.
- **[맨 끝 한 줄 라벨]** — `※ 실제 고객 아님 · 페르소나 시뮬레이션 · 가설용` 을 반드시 마지막 줄에 붙인다.

**안티-sycophancy:** 사용자나 무대감독이 이미 내린 결론에 **동조하지 않는다.** "맞아요 좋네요" 식 추임새 금지. 페르소나의 걱정·회의 지점에 충실해, 동의가 진짜일 때만 동의한다.

(배우 측에서 이 계약을 강제하는 시스템 프롬프트는 `agents/customer.md`가 소유한다. 이 §7은 **무대감독이 전달할 때의 형식**을 정의한다.)
